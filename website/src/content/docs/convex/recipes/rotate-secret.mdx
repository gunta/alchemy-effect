> Status: Convex env resources and promoted component metadata exist in source. Provider-side secret rotation can still require manual dashboard or provider API steps.

This recipe is for secrets that affect a live Convex app or its generated
integrations. The safe pattern is never "replace the value and hope." The safe
pattern is:

1. create a new secret name,
2. deploy code that can accept both values,
3. rotate the external provider,
4. verify the new secret is live,
5. remove the old secret in a later deploy.

The example below uses a webhook-style secret because it makes the two-secret
window explicit, but the same rollout shape applies to generated auth or
integration secrets.

## Why create a second secret instead of replacing the first one

A one-step replacement can break:

- webhook signature validation,
- OAuth callbacks that still rely on an old provider secret,
- generated app code that expects the old name during rollout,
- rollback, because old code no longer has the secret it expects.

Use versioned names during the transition, such as:

- `MUX_WEBHOOK_SECRET`
- `MUX_WEBHOOK_SECRET_NEXT`

## Step 1: Add the new secret without removing the old one

Model both names in deploy-time env resources and keep the old one live for
one full deploy cycle.

```ts
import * as Schema from "effect/Schema";
import { Mux } from "@alchemy/convex/components/mux";

const MuxLive = Mux.layer({
  name: "mux",
  env: {
    MUX_TOKEN_ID: Schema.String,
    MUX_TOKEN_SECRET: Schema.String,
    MUX_WEBHOOK_SECRET: Schema.String,
  },
});

yield* Convex.EnvironmentVariable("MuxWebhookSecretNext", {
  deployment,
  name: "MUX_WEBHOOK_SECRET_NEXT",
  value: Config.redacted("MUX_WEBHOOK_SECRET_NEXT"),
});
```

Your runtime verification logic should accept either secret during the overlap
window. Do not log either value.

## Step 2: Plan the change

Run:

```sh
alchemy plan
```

Expected plan shape:

```txt
Secrets
  + set MUX_WEBHOOK_SECRET       (redacted, no change)
  + set MUX_WEBHOOK_SECRET_NEXT  (redacted, create)
```

Two things should be true:

- the plan shows action names such as `create`, `update`, or `delete`,
- the secret values themselves never appear.

If the plan prints a literal secret value, stop. That is a bug in the product
contract.

## Step 3: Deploy code that accepts both values

Deploy before touching the external provider:

```sh
alchemy deploy
```

Expected deploy behavior:

- generated code and env wiring update first,
- Convex receives both secret names,
- existing traffic still validates against the old secret,
- new code is ready to validate the next secret too.

## Step 4: Rotate the external provider

Now update the third-party system to use the new secret. For a webhook
integration, that means changing the provider-side signing secret to
`MUX_WEBHOOK_SECRET_NEXT`.

This step is intentionally manual. The provider dashboard or API is the source
of truth for the remote secret.

## Step 5: Verify the new secret is actually live

Run another plan:

```sh
alchemy plan
```

Expected plan shape after provider rotation but before cleanup:

```txt
Secrets
  + set MUX_WEBHOOK_SECRET       (redacted, no change)
  + set MUX_WEBHOOK_SECRET_NEXT  (redacted, no change)
```

Then exercise one real request through the integration. The exact HTTP or app
verification step depends on the integration, but the important check is that
production traffic succeeds without falling back to the old secret.

## Step 6: Remove the old secret in a later deploy

Once the new secret is confirmed live, delete the old env var from the app
definition and remove the fallback path from code.

Run:

```sh
alchemy plan
alchemy deploy
```

Expected plan shape:

```txt
Secrets
  + delete MUX_WEBHOOK_SECRET    (redacted)
  + set MUX_WEBHOOK_SECRET_NEXT  (redacted, no change)
```

At that point you can rename `MUX_WEBHOOK_SECRET_NEXT` back to the canonical
name in a separate cleanup pass if your integration requires a stable name.

## What to verify in output and logs

The verification contract for secret rotation is:

- plan output shows the secret names but not the values,
- deploy logs show whether a secret is created, updated, or deleted,
- generated files and runtime logs do not print the secret bodies,
- rollback remains possible until the old secret is removed.

If you need a CI guard for generated files, run:

```sh
alchemy codegen --check
```

## Common caveats

- Better Auth and OAuth provider secrets often need a provider-side change as
  well as an app-side deploy. Treat both sides as part of one rotation.
- Session-signing secrets are usually higher risk than webhook secrets because
  they can invalidate active sessions. Plan a maintenance window if required by
  the auth system.
- Secret names are part of the rollout contract. Renaming and rotating in the
  same deploy is harder to recover from.

## When to stop and ask a human

Stop and get a human review if:

- the secret signs sessions, JWTs, or cookies that cannot safely accept a
  dual-secret window,
- you are rotating production auth provider secrets and do not know the exact
  callback or signing behavior,
- plan or deploy output shows a raw secret value anywhere,
- the external provider applies the rotation immediately and cannot overlap old
  and new values,
- the rollback plan depends on a secret you are about to delete.
