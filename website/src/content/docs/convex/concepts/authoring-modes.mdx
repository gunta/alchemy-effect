## Overview

The Convex integration supports four authoring modes because teams do
not all start from the same place:

- some already have a working `convex/` directory and only want Alchemy
  to manage infrastructure,
- some want an Effect-first typed DSL but still trust the Convex CLI as
  the deploy engine,
- some want a zero-files runtime push path and are willing to accept
  experimental risk,
- some are already invested in Confect.

The recommended default is **Alchemy Convex**.

## Comparison table

| Mode | Primary package | Best for | What Alchemy owns | What you still write | Risk |
| --- | --- | --- | --- | --- | --- |
| Alchemy Convex | `@alchemy/convex` + `@alchemy/convex-files` | New apps and Effect-first teams that still want the Convex CLI in the loop | Generated `convex/_alchemy/**`, component `convex.config.ts`, codegen manifest, and typed DSL integration | `App.make(...)`, `DatabaseSchema.make()`, groups, component installs, and migration metadata | Recommended default; some generated-file ownership discipline required |
| Alchemy Convex Runtime | `@alchemy/convex` + `@alchemy/convex-runtime` | Teams that want zero Convex files in git and accept an experimental deployer | Same DSL as Alchemy Convex, but deployed by the runtime push protocol instead of filesystem output | `App.make(...)` and app code only; no `convex/` directory required | Highest risk; direct protocol integration can drift with upstream Convex CLI behavior |
| Convex Plain | `@alchemy/convex-plain` or `alchemy/Convex` | Existing Convex apps that want Alchemy for infra only | Project, deployment, env vars, bindings, bundle/deploy orchestration | `convex/*.ts`, schema, HTTP routes, components, migrations in standard Convex form | Lowest migration risk, but fewer Alchemy-level guarantees around codegen and typed wrappers |
| Confect Adapter | `@alchemy/convex-confect` | Existing Confect users who want Alchemy around current workflows | Infra resources, deployment lifecycle, and Confect Adapter orchestration | Confect app definitions and Confect-specific authoring | Medium risk; adapter quality depends on Confect and Convex upstream stability |

## The decision tree

Start with the simplest question that matches your repository today:

1. If you are starting fresh and want Effect Schema, generated services,
   typed migrations, and explicit file ownership, use **Alchemy Convex**.
2. If you want the DSL from Alchemy Convex but specifically do not want a
   `convex/` directory on disk, use **Alchemy Convex Runtime** and accept that it is
   experimental.
3. If you already have a normal Convex app and do not want to rewrite
   it, use **Convex Plain**.
4. If your team already uses Confect and wants Alchemy to wrap it rather
   than replace it, use **Confect Adapter**.

## Convex Plain

Convex Plain keeps Convex authoring exactly as Convex users expect it today.
Alchemy manages the deploy-time surfaces around it.

All snippets on this page are fragments — they run inside the
`Effect.gen(function* () { ... })` body of an `Alchemy.Stack(...)`
declaration. See the [overview](/convex/) for the full stack shape.

```ts
import * as Convex from "@alchemy/convex-plain";

const project = yield* Convex.Project("MyApp", { slug: "my-app" });
const deployment = yield* Convex.Deployment("Dev", {
  project,
  type: "dev",
});
const code = yield* Convex.Bundle("Code", {
  deployment,
  source: "./convex",
});
```

Choose Convex Plain when stability and incremental adoption matter more
than a new authoring model.

## Alchemy Convex

Alchemy Convex is the golden path for new projects. You write an app in the
Alchemy DSL, and Alchemy generates the Convex-facing files into
`convex/_alchemy/` plus component config when needed before running the
normal Convex deployment flow.

```ts
import app from "./src/convex-app";
import * as Convex from "alchemy/Convex";
import { App } from "@alchemy/convex-files";

const project = yield* Convex.Project("MyApp", { slug: "my-app" });
const deployment = yield* Convex.Deployment("Dev", {
  project,
  type: "dev",
});
const backend = yield* App("Backend", {
  deployment,
  source: { app },
});
```

Why this is the default:

- the source of truth is typed application code,
- generated files have a clear owner,
- Convex's own CLI still verifies and deploys the app,
- the migration path to Alchemy Convex Runtime is designed to be one deployer swap.

## Alchemy Convex Runtime

Alchemy Convex Runtime uses the same DSL as Alchemy Convex but skips on-disk Convex files
and pushes a synthesized bundle directly to Convex's deploy protocol.

```ts
import app from "./src/convex/app";
import * as Convex from "alchemy/Convex";
import { App } from "@alchemy/convex-runtime";

const project = yield* Convex.Project("MyApp", { slug: "my-app" });
const deployment = yield* Convex.Deployment("Dev", {
  project,
  type: "dev",
});
const backend = yield* App("Backend", {
  deployment,
  source: { app },
});
```

This mode exists for teams that want the strongest "one program"
story, but it is explicitly experimental because it depends on close
protocol compatibility with Convex's own tooling.

## Confect Adapter

Confect Adapter keeps Confect as the authoring layer and adds Alchemy around
it for project, deployment, env, and host integration.

```ts
import confectApp from "./confect/app";
import * as Convex from "alchemy/Convex";
import { App } from "@alchemy/convex-confect";

const project = yield* Convex.Project("MyApp", { slug: "my-app" });
const deployment = yield* Convex.Deployment("Dev", {
  project,
  type: "dev",
});
const backend = yield* App("Backend", {
  deployment,
  source: { app: confectApp },
});
```

This is the path for teams that want better infrastructure composition
without migrating their app model immediately.

## What changes between Alchemy Convex and Alchemy Convex Runtime

Alchemy Convex and Alchemy Convex Runtime intentionally share the same app DSL. The
difference is the deployer:

| Surface | Alchemy Convex | Alchemy Convex Runtime |
| --- | --- | --- |
| Source of truth | `App.make(...)` | `App.make(...)` |
| Generated files on disk | Yes, under `convex/_alchemy/**` plus `convex/convex.config.ts` when components are declared | No |
| Final deploy path | `convex deploy` | Runtime `deploy2` protocol |
| Stability target | Default production path | Experimental |

That shared contract is important because it keeps teams from getting
locked into one deployment mechanism.

## Mixing and migration rules

- Convex Plain can coexist with some DSL-authored helper code if you want to
  adopt pieces gradually.
- Alchemy Convex and Alchemy Convex Runtime are alternative deployers for the same DSL output, so
  they should not manage the same deployment at the same time.
- Moving from Alchemy Convex to Alchemy Convex Runtime is intended to be an import swap plus
  operational review, not a rewrite of your schema and handlers.

If you are unsure, start with Alchemy Convex. It gives the implementation the
clearest contract while staying closest to the normal Convex workflow.
