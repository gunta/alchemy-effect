> Status: the DSL file map and `@alchemy/convex-files` sink exist in
> source. They generate `convex/_alchemy/**` and, when components are
> declared, a generated `convex/convex.config.ts`. Migration codegen also
> emits `convex/_alchemy/migrations.ts`,
> `convex/_alchemy/migrations.manifest.json`, and the stable
> `convex/migrations.ts` re-export. The files deployer validates source
> props before filesystem work, tracks generated-file ownership, can
> prepare files without invoking the CLI on dry runs, and refuses unowned
> or drifted files unless adoption is explicit.

## Overview

The generated-file contract exists to answer a boring but critical
question: when Alchemy and Convex both touch a repository, who owns
which file?

The rule is simple:

- user-authored files stay user-authored,
- Convex-owned generated files stay Convex-owned,
- Alchemy writes only to clearly scoped generated locations,
- drift is reported explicitly instead of being silently repaired during
  CI checks.

This page describes the ownership model and calls out the surfaces that
are generated versus deliberately left to the user.

## Ownership table

| Path | Owner | When it changes | Drift behavior |
| --- | --- | --- | --- |
| `alchemy.run.ts` and stack entrypoints | User | When you change infrastructure or app composition | Alchemy never generates or overwrites it |
| `convex/schema.ts` in Convex Plain | User | When you edit the app schema by hand | Alchemy reads only |
| `convex/*.ts` in Convex Plain | User | When you change handlers, routes, crons, or component wiring by hand | Alchemy reads only, except for explicitly requested scaffolds |
| `convex/_alchemy/**` | Alchemy | When DSL codegen output changes | Overwritten on codegen; manual edits are warned on by the file manifest and may be refused in strict checks |
| `convex/convex.config.ts` in Alchemy Convex | Alchemy-generated when components are declared | When component installs or typed env declarations change | Tracked by the generated-file manifest; unowned collisions are refused unless adopted |
| `convex/http.ts` in Alchemy Convex | Alchemy-generated when `App.make({ http })` is declared | When generated HTTP routes change | Tracked by the generated-file manifest; unowned collisions are refused unless adopted |
| `convex/auth.ts` and `convex/auth.config.ts` | Mode-dependent | When auth mode or provider configuration changes | Ownership depends on the selected auth integration and must be documented by that mode |
| `convex/migrations.ts` | User-facing stable re-export | When generated migration modules change | Top-level file stays a stable re-export; generated implementation lives under `_alchemy` |
| `convex/_generated/**` | Convex CLI / Convex backend | When Convex codegen runs | Alchemy never writes here directly |
| `node_modules/**` | Package manager | When dependencies are installed or upgraded | Alchemy does not patch installed packages |
| `.env.local` | User | During local development only | Alchemy may read it when explicitly configured, but production env should go through resources |

## Mode-specific rules

The ownership story changes by mode:

| Mode | Generated files | What that means |
| --- | --- | --- |
| Convex Plain | None required by Alchemy | Your `convex/` directory remains a normal Convex app; Alchemy manages infra and deployment only |
| Alchemy Convex | `convex/_alchemy/**` plus generated top-level shims for declared DSL surfaces | Alchemy generates the Convex-facing modules and refuses unowned top-level collisions unless adopted |
| Alchemy Convex Runtime | No on-disk Convex files required | The same codegen exists conceptually, but the sink is an in-memory file map instead of the filesystem |
| Confect Adapter | Depends on Confect output | The Confect Adapter should respect Confect's ownership model and add Alchemy-managed deployment surfaces around it |

## The stable re-export pattern

Alchemy Convex avoids comment markers and large-scale file
rewriting for generated internals. The implemented compiler emits
`convex/_alchemy/schema.ts`, `convex/_alchemy/<group>.ts`,
`convex/_alchemy/runtime.ts`, and `convex/_alchemy/manifest.json`.

When component installs exist, it also emits a complete
`convex/convex.config.ts`:

```ts
import { defineApp } from "convex/server";
import { v } from "convex/values";
import rag from "@convex-dev/rag/convex.config.js";

const app = defineApp({
  env: {
    OPENAI_API_KEY: v.string(),
  },
});

app.use(rag, {
  name: "rag",
  env: { OPENAI_API_KEY: app.env.OPENAI_API_KEY },
});

export default app;
```

Generated top-level shims such as `convex/http.ts` and
`convex/migrations.ts` follow the same conservative rule as
`convex/convex.config.ts`: Alchemy writes the file only when the DSL
declares the matching surface, tracks it in the manifest, and refuses to
overwrite unrelated user code unless `adoptGenerated` is explicitly set.

## Drift checks

`alchemy codegen --check` is the intended CI-friendly way to validate
that generated files still match the source app definition.

```txt
convex/_alchemy/schema.ts drifted
  expected: generated from alchemy.run.ts
  actual: manual edit detected

Run: alchemy codegen
```

Check mode should:

- print exact drift instead of silently rewriting files,
- fail CI when generated files differ from the expected output,
- make manual edits to `convex/_alchemy/**` visible immediately,
- keep normal `alchemy codegen` as the explicit repair step.

## Files deployer behavior

`@alchemy/convex-files` is the deployer package for the recommended
Alchemy Convex mode. Its deploy boundary has two phases:

1. compile the DSL app and synchronize the generated file map to disk,
2. optionally delegate to the shared `ConvexCli` service for bundle
   deployment.

The first phase validates `source: { app, outDir, adoptGenerated,
cleanGenerated, bundle }` before touching the filesystem. It writes a
manifest that records generated ownership and refuses to overwrite
unowned files unless `adoptGenerated` is set. When `cleanGenerated` is
enabled, stale generated files are removed only if the manifest still
proves ownership.

The second phase is intentionally optional. On dry runs, the deployer
prepares generated files and computes generated state without invoking
the Convex CLI. When bundle deployment is requested and a `ConvexCli`
layer is available, the default CLI source is the generated `convex`
directory under `outDir`.

This split lets tests and CI validate generated-file state without
needing Convex credentials, while production deploys can still use the
normal Convex CLI path.

## Generated top-level files

Some top-level files are generated only for specific DSL surfaces. If the
surface is not declared, Alchemy leaves the file alone. If the surface is
declared and an unrelated file already exists at that path, the files
deployer reports an unowned-file collision instead of silently merging or
overwriting it.

Auth-related files may be user-owned or generated depending on whether
the chosen auth mode is raw JWT providers, Convex Auth, or Better Auth.
That ownership decision belongs to the selected auth integration rather
than the generic file writer.

## Recommended workflow

The docs and examples recommend this operational model for Alchemy Convex:

1. Author the app in the DSL.
2. Run `alchemy codegen` locally.
3. Let Convex generate `convex/_generated/**` through its normal flow.
4. Run `alchemy codegen --check` in CI before type checking or deploy.

That sequence keeps ownership explicit for both systems:

- Alchemy owns the code it synthesizes from the DSL.
- Convex owns the code it synthesizes from the deployed app structure.
- The user owns the infrastructure entrypoint and the human-authored app
  code.
