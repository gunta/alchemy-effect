> Status: the promoted wrappers for Workpool, Workflow, Action Retrier, and
> Action Cache are exported as explicit modules under
> `@alchemy/convex/components/*` with install metadata and Effect service
> tags.

Convex has multiple ways to run background or durable work, and they solve
different problems. The Alchemy wrappers keep those distinctions
visible instead of collapsing everything into a single queue abstraction.

## Choose the right component

| Wrapper | Use it for | Do not use it for |
| --- | --- | --- |
| `Workpool` | Bounded parallelism and job queue style fan-out | Long-lived deterministic workflows |
| `Workflow` | Multi-step durable flows with status and event history | High-volume fire-and-forget job ingestion |
| `ActionRetrier` | One idempotent action that may need retries | Rich orchestration across many steps |
| `ActionCache` | Reusing expensive action results behind a TTL | Query or mutation result caching |

## Workpool

`Workpool` is the queue primitive for bounded parallelism. Like
every promoted component, it has two faces:

- `Workpool.layer(...)` returns an Effect Layer with component
  install metadata attached. Pass the same value to
  `App.make({ components: { ... } })` and `Effect.provide(...)`.
- `Workpool` is an Effect service you `yield*` from a handler
  to enqueue jobs and read status.

Declare the install in the app file:

```ts
import * as Duration from "effect/Duration";
import { Workpool } from "@alchemy/convex/components/workpool";

const ImageWorkLive = Workpool.layer({
  name: "imageWork",
  options: {
    maxParallelism: 20,
    retryActionsByDefault: false,
    defaultRetryBehavior: {
      maxAttempts: 5,
      initialBackoff: Duration.millis(250),
      base: 2,
    },
  },
});
```

Service surface:

| Method | Purpose |
| --- | --- |
| `enqueueAction`, `enqueueMutation`, `enqueueQuery` | Add one job |
| Batch variants | Add many jobs efficiently |
| `status`, `statusBatch` | Read job state |
| `cancel`, `cancelAll` | Stop queued or running jobs where supported |
| `config.update(...)` | Change `maxParallelism` or `logLevel` |

Important rules:

- Retry should stay explicit unless `retryActionsByDefault` is deliberately
  enabled.
- `maxParallelism: 0` is the pause switch.
- Completion handlers are generated Convex functions, not ad hoc runtime callbacks.

## Workflow

`Workflow` is for long-running deterministic flows that need
status, restart, cancel, and event control.

Declare a typed handle alongside the implementation. `.ref<...>()` is a
type-only helper that names the workflow and its arg/return types:

```ts
import { Workflow } from "@alchemy/convex/components/workflow";

const OnboardUser = Workflow.ref<
  { userId: string },
  { completedAt: number }
>("onboardUser", internal.workflows.onboardUser);
```

Inside a mutation/action handler, `yield* Workflow` to get the
service, then call `start`:

```ts
const workflow = yield* Workflow;
yield* workflow.start(OnboardUser, { userId }, { idempotencyKey: userId });
```

Service methods: `start`, `status`, `cancel`, `restart`,
`sendEvent`, `createEvent`, `list`, `listSteps`, and `cleanup`.

Workflow caveats:

- Keep workflow code deterministic.
- Do not call raw `fetch`, unstable env reads, or unscoped crypto directly in
  workflow bodies.
- Prefer storing large payloads by ID instead of inlining them into the run state.

## Action Retrier

Use `ActionRetrier` when the unit of work is still "one action",
but it needs retry policy and durable status. Install it on the app:

```ts
import { ActionRetrier } from "@alchemy/convex/components/action-retrier";

const ActionRetrierLive = ActionRetrier.layer({
  name: "actionRetrier",
  options: {
    defaults: {
      initialBackoff: Duration.millis(250),
      base: 2,
      maxFailures: 4,
      idempotency: "required",
    },
  },
});
```

Then `yield* ActionRetrier` inside the handler to call `run`,
`status`, etc.

Service methods: `run`, `status`, and `cancel`.

The docs should keep one rule front and center: retried actions must define
an idempotency policy because Convex actions are free to perform external side
effects.

## Action Cache

`ActionCache` is a typed cache for expensive action results.
Install one entry per cached action:

```ts
import { ActionCache } from "@alchemy/convex/components/action-cache";

const EmbeddingsCacheLive = ActionCache.layer({
  name: "embeddingsCache",
  options: {
    action: internal.embeddings.embed,
    cacheName: "embed-v1",
    ttl: Duration.days(7),
  },
});
```

`yield* ActionCache` in an action handler to `get`, `set`,
`invalidate`, or `invalidateAll`.

Service methods: `get`, `set`, `invalidate`, and `invalidateAll`.

Important caveats:

- `fetch` is action-context only.
- TTL semantics are "the shorter of stored TTL and per-call TTL".
- `force` recomputes for the caller, but it is not a distributed single-flight lock.

## Testing expectations

| Wrapper | Testing focus |
| --- | --- |
| Workpool | Multi-pool isolation, pause mode, cancel/status behavior, codegen snapshots |
| Workflow | Deterministic runs, component child workpool integration, restart and cleanup |
| Action Retrier | Retry-then-success, delayed runs, cancel paths, callback failure |
| Action Cache | Hit/miss, TTL, `force`, duplicate compute on concurrent misses |

## Caveats

- These wrappers should mirror upstream naming where possible instead of
  inventing a second job vocabulary.
- None of these abstractions should quietly downgrade app-owned auth or
  validation choices.
- Workflow and job orchestration are operational features, so the plan output
  should stay clear about installs, generated functions, and follow-up commands.
