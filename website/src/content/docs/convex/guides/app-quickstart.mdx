> This page documents the planned Convex integration API. It is the product contract for the implementation pass.

This is the **recommended Convex starting point** in Alchemy:
**Alchemy DSL + Files**.

You author one typed app definition with Effect Schema and Effect
handlers. Alchemy compiles that app into generated Convex files under
`convex/_alchemy/`, keeps a few stable top-level re-exports in
`convex/`, and then runs a normal `convex deploy`.

That gives you three useful properties at once:

- a strongly typed application authoring model
- generated Convex-compatible files you can inspect in git
- the standard Convex CLI still in the loop for deploys

If you already have a Plain Convex app you want to keep as-is, start
with [Convex Quickstart](/convex/guides/quickstart) instead.

## What you will build

This guide walks the full golden path from the design spec:

1. Create a Convex app declaration.
2. Define the schema.
3. Define a query, mutation, and action.
4. Add an HTTP route.
5. Add Better Auth.
6. Add Cloudflare R2.
7. Add RateLimiter.
8. Add an online migration.
9. Run `alchemy plan` and inspect the output.
10. Deploy.
11. Run or wait for the migration.
12. See the contract gate that prevents unsafe contraction.

All APIs below are **planned package names and shapes**. They are
intentionally specific so implementation can converge on them.

## Prerequisites

- Bun installed
- A Convex account and deployment credentials
- A project directory with `alchemy.run.ts`
- Willingness to let Alchemy own `convex/_alchemy/**`

Alchemy DSL + Files keeps ownership boundaries explicit:

- `src/convex/app.ts` is user-owned
- `convex/_alchemy/**` is generated by Alchemy
- top-level files such as `convex/migrations.ts` are stable re-exports
  or merge-managed shims

## Install the planned packages

```sh
bun add alchemy convex effect @alchemy/convex @alchemy/convex-dsl @alchemy/convex-files
```

The important split is:

- `@alchemy/convex` for the core project and deployment resources
- `@alchemy/convex-dsl` for the authoring API
- `@alchemy/convex-files` for the file-writing deployer

## Project layout

A typical Alchemy DSL + Files app looks like this:

```txt
.
├── alchemy.run.ts
├── src
│   └── convex
│       ├── app.ts
│       ├── notes.ts
│       └── auth.ts
└── convex
    ├── _alchemy/            # generated by Alchemy
    ├── convex.config.ts     # merge-managed
    ├── http.ts              # merge-managed
    └── migrations.ts        # stable re-export
```

You write the app declaration under `src/convex/`. Alchemy compiles
it into the files Convex expects.

## Step 1: Define the schema

The schema is authored with Effect Schema, then compiled into Convex
validators and generated modules.

```ts
// src/convex/schema.ts
import * as Schema from "effect/Schema";
import { defineSchema, table } from "@alchemy/convex-dsl";

export const schema = defineSchema({
  users: table(
    Schema.Struct({
      email: Schema.String,
      displayName: Schema.optionalKey(Schema.String),
    }),
  ).index("by_email", ["email"]),

  notes: table(
    Schema.Struct({
      text: Schema.String,
      title: Schema.optionalKey(Schema.String),
      authorId: Schema.String,
      attachmentKey: Schema.optionalKey(Schema.String),
    }),
  )
    .index("by_author", ["authorId"])
    .searchIndex("by_text", { searchField: "text" }),
});
```

`Schema.optionalKey` is the Effect 4 spelling for "field may be absent."
Use it rather than `Schema.optional`, which means "the value may be
`T | undefined`" — a different runtime shape.

The key design constraint is that the schema must stay in the
compileable Convex subset. That is what lets Alchemy generate
validators everywhere instead of falling back to untyped runtime
surprises.

## Step 2: Define typed functions

Define groups with `query`, `mutation`, and `action`. Business logic
lives in Effects; generated Convex wrappers stay thin.

```ts
// src/convex/notes.ts
import * as Effect from "effect/Effect";
import * as Schema from "effect/Schema";
import { defineGroup, query, mutation, action } from "@alchemy/convex-dsl";
import {
  DatabaseReader,
  DatabaseWriter,
  QueryRunner,
} from "@alchemy/convex-dsl/server";
import { schema } from "./schema";

export const notes = defineGroup("notes", {
  list: query({
    args: Schema.Struct({}),
    returns: Schema.Array(schema.tables.notes.doc),
    handler: () =>
      Effect.gen(function* () {
        const db = yield* DatabaseReader;
        return yield* db.table("notes").collect();
      }),
  }),

  create: mutation({
    args: Schema.Struct({
      text: Schema.String,
      authorId: Schema.String,
    }),
    returns: schema.tables.notes.id,
    handler: ({ text, authorId }) =>
      Effect.gen(function* () {
        const db = yield* DatabaseWriter;
        return yield* db.table("notes").insert({
          text,
          title: text.slice(0, 40),
          authorId,
        });
      }),
  }),

  summarize: action({
    args: Schema.Struct({
      noteId: schema.tables.notes.id,
    }),
    returns: Schema.String,
    handler: ({ noteId }) =>
      Effect.gen(function* () {
        const queries = yield* QueryRunner;
        const note = yield* queries.notes.get({ noteId });
        return note.text.slice(0, 120);
      }),
  }),
});
```

Three design rules are doing real work here:

- validators are generated from the same schemas you author
- handlers depend on typed services rather than raw Convex context
- return types are explicit, so client code can decode safely

## Step 3: Add an HTTP route

HTTP routes are part of the app declaration rather than stray
side-car code.

```ts
// src/convex/http.ts
import * as Effect from "effect/Effect";
import * as Layer from "effect/Layer";
import * as Schema from "effect/Schema";
import * as HttpApi from "effect/unstable/httpapi/HttpApi";
import * as HttpApiBuilder from "effect/unstable/httpapi/HttpApiBuilder";
import * as HttpApiEndpoint from "effect/unstable/httpapi/HttpApiEndpoint";
import * as HttpApiGroup from "effect/unstable/httpapi/HttpApiGroup";
import { defineHttp } from "@alchemy/convex-dsl";

class Health extends Schema.Class<Health>("Health")({
  ok: Schema.Boolean,
}) {}

const ping = HttpApiEndpoint.get("ping", "/health", {
  success: Health,
});

class HealthGroup extends HttpApiGroup.make("Health").add(ping) {}
class Api extends HttpApi.make("Api").add(HealthGroup) {}

const ApiLive = HttpApiBuilder.group(Api, "Health", (handlers) =>
  handlers.handle("ping", () => Effect.succeed(new Health({ ok: true }))),
);

export const http = defineHttp({
  "/": {
    api: Api,
    layer: ApiLive,
  },
});
```

The generated `convex/http.ts` stays merge-managed. You author the
route intent; Alchemy owns the generated glue.

## Step 4: Add Better Auth

Better Auth is a flagship promoted wrapper. The app should declare it
as a component install instead of hand-wiring deploy-time details in
multiple files.

```ts
// src/convex/auth.ts
import { defineGroup, mutation } from "@alchemy/convex-dsl";
import * as Effect from "effect/Effect";
import * as Schema from "effect/Schema";
import { Components } from "@alchemy/convex-dsl/components";

export const auth = defineGroup("auth", {
  signIn: mutation({
    args: Schema.Struct({
      email: Schema.String,
      password: Schema.String,
    }),
    returns: Schema.Struct({ ok: Schema.Boolean }),
    handler: ({ email, password }) =>
      Effect.gen(function* () {
        const betterAuth = yield* Components.BetterAuth;
        yield* betterAuth.signIn.email({
          email,
          password,
        });
        return { ok: true };
      }),
  }),
});
```

At deploy time, the wrapper is expected to drive:

- generated auth routes
- required env vars such as `BETTER_AUTH_SECRET`
- component installation in `convex.config.ts`
- any stable generated shims the app needs

## Step 5: Add Cloudflare R2

R2 is where the broader Alchemy story becomes obvious: Convex app code
and cloud infrastructure compose in one stack.

```ts
// alchemy.run.ts excerpt — inside Alchemy.Stack's Effect.gen body
import * as Cloudflare from "alchemy/Cloudflare";

const uploads = yield* Cloudflare.R2Bucket("Uploads", {});
```

Then the app declares the official Convex component through the Alchemy
wrapper. The important contract is that Alchemy owns the Cloudflare bucket,
credentials, env vars, and component install, while generated Convex code still
uses the upstream `@convex-dev/r2` API:

```ts
// alchemy.run.ts excerpt
const uploadsR2 = yield* Components.R2("uploads", {
  component: "r2",
  bucket: uploads,
  credentials: {
    accessKeyId: Config.redacted("R2_ACCESS_KEY_ID"),
    secretAccessKey: Config.redacted("R2_SECRET_ACCESS_KEY"),
    token: Config.redacted("R2_TOKEN"),
  },
  client: {
    module: "files",
    exposeClientApi: {
      checkUpload: "requireFileUpload",
      checkDelete: "requireFileDelete",
    },
  },
});
```

Alchemy generates ordinary Convex code around the official component:

```ts
// convex/files.ts
import { R2 } from "@convex-dev/r2";
import { components } from "./_generated/api";
import type { DataModel } from "./_generated/dataModel";

export const r2 = new R2(components.r2);

export const {
  generateUploadUrl,
  syncMetadata,
  getMetadata,
  listMetadata,
  deleteObject,
} = r2.clientApi<DataModel>({
  checkUpload: requireFileUpload,
  checkDelete: requireFileDelete,
});
```

Frontend code can then use the official hook. This snippet runs inside a
React component, not inside the Alchemy stack body, so `await` is
appropriate here:

```tsx
// React component, not Alchemy stack code
import { useUploadFile } from "@convex-dev/r2/react";
import { api } from "../convex/_generated/api";

const uploadFile = useUploadFile(api.files);
const key = await uploadFile(file);
```

The goal is not just "talk to R2 from Convex." The goal is a typed
bridge between cloud resource ownership and Convex metadata,
upload flows, and generated helpers without hiding the upstream component.

## Step 6: Add RateLimiter

The plan explicitly calls for an operational component so the quickstart
shows more than CRUD.

Use RateLimiter to gate failed login attempts. `Components.RateLimiter.use(...)`
returns a `ComponentInstall` value the app declaration consumes — it is not
itself an Effect, so it does **not** sit inside `Effect.gen`:

```ts
// src/convex/app.ts
import * as Duration from "effect/Duration";
import { Components } from "@alchemy/convex-dsl/components";

const rateLimiter = Components.RateLimiter.use("rateLimiter", {
  rates: {
    failedLogins: {
      kind: "fixed window",
      rate: 5,
      period: Duration.minutes(15),
    },
  },
});
```

Pass it through `defineApp({ components: [rateLimiter, ...] })` (see Step 8)
and then call it from the auth mutation before you perform the actual
sign-in flow.

## Step 7: Add an online migration

Migrations are first-class in the DSL because production rollouts
should model **expand, backfill, and contract** explicitly.

```ts
// src/convex/migrations.ts
import * as Effect from "effect/Effect";
import { defineMigrations } from "@alchemy/convex-dsl";
import { schema } from "./schema";

export const migrations = defineMigrations((m) => [
  m.online("20260519_note_titles", {
    strategy: "dual-read",
    table: schema.tables.notes,
    batchSize: 100,
    migrateOne: (note) =>
      Effect.succeed(
        note.title !== undefined
          ? {}
          : { title: note.text.slice(0, 40) },
      ),
    verify: {
      remaining: (q) =>
        q.filter((q) => q.eq(q.field("title"), undefined)),
    },
    contract: {
      summary: "require title everywhere after verification is clean",
      after: "completed",
    },
  }),
]);
```

The safe path is the point:

- **expand** deploys code and schema that tolerate both shapes
- **backfill** updates existing documents while traffic continues
- **contract** remains blocked until verification is clean

## Step 8: Define the app

This is the required golden-path block from the plan. Keep this shape
stable unless the design changes on purpose.

```ts
const app = defineApp({
  schema,
  groups: { notes, auth },
  components: [
    Components.RateLimiter.use("rateLimiter", {
      rates: {
        failedLogins: {
          kind: "fixed window",
          rate: 5,
          period: Duration.minutes(15),
        },
      },
    }),
  ],
  migrations,
});
```

In the full quickstart, the app also wires `http`, Better Auth, and
RateLimiter alongside those groups and migrations. R2 is declared in
`alchemy.run.ts` because it consumes `Cloudflare.R2Bucket`; Alchemy then
installs `@convex-dev/r2` into the generated `convex.config.ts`.

```ts
// src/convex/app.ts
import { defineApp } from "@alchemy/convex-dsl";
import { Components } from "@alchemy/convex-dsl/components";
import { schema } from "./schema";
import { notes } from "./notes";
import { auth } from "./auth";
import { http } from "./http";
import { migrations } from "./migrations";

export default defineApp({
  schema,
  groups: { notes, auth },
  http,
  components: [
    Components.BetterAuth.use("betterAuth", {
      siteUrl: "https://app.example.com",
      basePath: "/api/auth",
    }),
    Components.RateLimiter.use("rateLimiter", {
      rates: {
        failedLogins: {
          kind: "fixed window",
          rate: 5,
          period: Duration.minutes(15),
        },
      },
    }),
  ],
  migrations,
});
```

The design goal is that one declaration tells you what the backend is:
schema, groups, routes, components, and rollout policy.

## Step 9: Bind the app in `alchemy.run.ts`

Alchemy DSL + Files uses the files deployer. It generates the shared code under
`convex/_alchemy/` and then runs a normal Convex deploy from the file
tree.

```ts
// alchemy.run.ts
import * as Alchemy from "alchemy";
import * as Convex from "@alchemy/convex";
import { App } from "@alchemy/convex-files";
import * as Cloudflare from "alchemy/Cloudflare";
import * as Config from "effect/Config";
import * as Effect from "effect/Effect";
import * as Duration from "effect/Duration";
import * as Layer from "effect/Layer";
import app from "./src/convex/app";

export default Alchemy.Stack(
  "ConvexDslApp",
  {
    providers: Layer.mergeAll(
      Convex.providers(),
      Cloudflare.providers(),
    ),
    state: Alchemy.localState(),
  },
  Effect.gen(function* () {
    const uploads = yield* Cloudflare.R2Bucket("Uploads");

    const backend = yield* App("Backend", {
      app,
      project: "notes-app",
      type: "prod",
      migrations: {
        phase: "backfill",
        run: "wait",
        dryRunFirst: true,
        timeout: Duration.minutes(30),
        production: {
          allowContract: false,
          requireCleanVerify: true,
        },
      },
      env: {
        BETTER_AUTH_SECRET: Config.redacted("BETTER_AUTH_SECRET"),
        SITE_URL: "https://app.example.com",
        R2_BUCKET: uploads.bucketName,
        R2_ENDPOINT: Config.string("R2_ENDPOINT"),
        R2_TOKEN: Config.redacted("R2_TOKEN"),
        R2_ACCESS_KEY_ID: Config.redacted("R2_ACCESS_KEY_ID"),
        R2_SECRET_ACCESS_KEY: Config.redacted("R2_SECRET_ACCESS_KEY"),
      },
    });

    return {
      deploymentUrl: backend.deploymentUrl,
    };
  }),
);
```

The key Alchemy DSL + Files contract is:

- user code lives in the DSL
- generated files live in `convex/_alchemy`
- deploy still flows through Convex's normal file-based tooling

## Step 10: Run a plan

Before the first deploy, run:

```sh
bun alchemy plan
```

The intended plan output should read like an operational checklist,
not a blob of infrastructure diff. Expect categories such as:

- codegen writes and merges
- component installs
- secrets
- generated HTTP routes
- migration phase status
- post-deploy commands when Alchemy is not running them for you

The important thing to inspect is not just "will it deploy?" but also:

- which generated files Alchemy plans to write
- which secrets will be created or updated
- which components will be installed
- whether the migration is in expand, backfill, or contract mode
- whether contract is currently blocked

## Step 11: Deploy

Deploy the stack:

```sh
bun alchemy deploy
```

For the golden path, the first production-grade deploy should look
roughly like this:

1. compile the app into generated files
2. merge top-level Convex shims such as `convex.config.ts`
3. install components such as Better Auth, R2, and RateLimiter
4. set deployment environment variables
5. run `convex deploy`
6. optionally start and wait for migrations, depending on the chosen
   migration mode

## Step 12: Run or wait for the migration

There are two good starting postures:

- `run: "manual"` if you want the deploy to print the exact migration
  commands and stop
- `run: "wait"` if you want Alchemy to start the migration and poll
  until it completes or times out

For manual mode, the intended commands are shaped like:

```sh
convex run migrations:runPending '{}'
convex run migrations:verifyNoteTitles '{}'
```

For `run: "wait"`, Alchemy should handle the start and polling but
still surface the same verification intent in plan output and errors.

## Step 13: Understand the contract gate

The migration guide is built around one non-negotiable production
guardrail:

**contract steps stay blocked until verification is clean.**

That means a deploy may legitimately tell you:

- expand is ready
- backfill is pending or running
- contract is blocked

This is a feature, not friction. It prevents a schema or code
contraction that would strand old-format documents in production.

## Generated files you should expect

Alchemy DSL + Files uses shared codegen to produce the Convex-facing files.
Important outputs include:

- `convex/_alchemy/manifest.json`
- `convex/_alchemy/runtime.ts`
- `convex/_alchemy/refs.ts`
- `convex/_alchemy/services.ts`
- `convex/_alchemy/migrations.ts`
- merge-managed `convex/http.ts`
- merge-managed `convex/convex.config.ts`

Treat `convex/_alchemy/**` as Alchemy-owned. If you want review
protection in CI, the planned contract includes a generated-file
check mode instead of silent rewrites.

## When to choose Alchemy DSL + Runtime instead

Alchemy DSL + Files is the default because it keeps Convex's CLI and generated
file model in the loop. Reach for
[Convex Runtime Deployer](/convex/guides/runtime-experimental) only
when you specifically want:

- zero Convex files committed in the repo
- direct runtime pushes via the `deploy2` protocol
- an experimental workflow with stricter drift risk

For most teams, Alchemy DSL + Files is the best balance of clarity, safety, and
power.
