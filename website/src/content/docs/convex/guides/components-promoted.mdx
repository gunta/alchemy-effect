> Status: generic component installs are implemented through
> `defineComponentUse(...)` in `@alchemy/convex`, the core
> `Convex.Component` resource exists, promoted component modules are imported
> one-by-one from `@alchemy/convex/components/*`, and the metadata catalog
> is available from `@alchemy/convex/components/catalog`.

Promoted wrappers exist for the components that become materially better when
Alchemy adds typed services, generated files, or deploy-time safety. Every
promoted wrapper still builds on the same generic substrate, so you can start
generic and adopt a richer wrapper later without changing the ownership model.

## Start with the generic substrate

When a component is not promoted yet, or when you want to use a new upstream
feature immediately, use the generic install surface first:

```ts
import { defineComponentUse } from "@alchemy/convex";

const geospatial = defineComponentUse("geospatial", {
  source: {
    package: "@convex-dev/geospatial",
    version: "^0.2.1",
    configExport: "@convex-dev/geospatial/convex.config.js",
  },
  name: "geospatial",
  test: "@convex-dev/geospatial/test",
});
```

Supported generic props (matches the [components concept](/convex/concepts/components#generic-install-shape)):

| Prop | Meaning |
| --- | --- |
| `source` | npm package or local component folder |
| `name` | Install key under `components.<name>` |
| `env` | Typed env declarations passed into `app.use(component, { env })` |
| `httpPrefix` | Mount point for public component routes; omitted means no public HTTP routes |
| `options` | Raw install options for new upstream features |
| `test` | Optional component test entrypoint |

Use the generic route whenever you need the escape hatch. Use
`Convex.Component(...)` when a Convex Plain stack wants component install
metadata tracked as an Alchemy resource rather than generated from
`App.make(...)`.

## What promotion adds

A promoted wrapper adds three things on top of the generic component
install:

1. Typed install metadata such as a tested package range and default name.
2. An app-side `Context.Service` layer with `Effect`-returning methods.
3. Codegen hooks for imports, helper modules, route registration, or tests.

The runtime layer is the app boundary. It can depend on generated refs,
`Auth`, scheduler services, storage, or env, but it must not close over
management credentials or provider SDK clients.

## Maturity tiers

| Tier | Meaning | Components |
| --- | --- | --- |
| A - flagship | Detailed guide, generated code, test helper integration, Effect service, example app coverage | Migrations, Better Auth, R2, RateLimiter, Workflow, Workpool |
| B - typed client | Generic install plus Effect service and tests, but usually no full example app | Aggregate, ShardedCounter, Geospatial, Crons, ActionCache, ActionRetrier, Agent, Authz |
| C - integration bridge | Needs external services, webhooks, or scaffold behavior | Mux, NeutralCost |
| D - generic | Works through `defineComponentUse(...)` or `Convex.Component(...)` only | Any unsupported component |

## Example: One Layer for Install Metadata and Runtime Service

The promoted wrappers expose `Effect` services rather than raw
`ctx.runMutation` calls. The same Layer can also be handed to
`App.make({ components })`, because Alchemy attaches component install
metadata to promoted component layers:

```ts
import { App, Group, Mutation } from "@alchemy/convex";
import { R2 } from "@alchemy/convex/components/r2";
import { RateLimiter } from "@alchemy/convex/components/rate-limiter";
import * as Effect from "effect/Effect";

const RateLimiterLive = RateLimiter.layer({
  name: "rateLimiter",
  rates: {
    failedLogins: {
      kind: "fixed window",
      rate: 5,
      periodMs: 15 * 60 * 1000,
    },
  },
  service: {
    limit: (name, request) =>
      Effect.succeed({
        name,
        key: request?.key,
        allowed: true,
      }),
    check: (name, request) =>
      Effect.succeed({
        name,
        key: request?.key,
        allowed: true,
      }),
    reset: () => Effect.void,
  },
});

const R2Live = R2.layer();

export const app = App.make({
  components: {
    r2: R2Live,
    rateLimiter: RateLimiterLive,
  },
});

const auth = Group.make("auth", {
  signIn: Mutation.make({
    args: SignInArgs,
    handler: (args) =>
      Effect.gen(function* () {
        const limiter = yield* RateLimiter;
        yield* limiter.limit("failedLogins", { key: args.email, throws: true });
        return yield* signInImpl(args);
      }).pipe(Effect.provide(RateLimiterLive)),
  }),
});
```

## HTTP, env, and tests

| Concern | Rule |
| --- | --- |
| Component env | Declare typed env in `convex.config.ts` when upstream supports it |
| Public HTTP routes | Mounted only when `httpPrefix` is set, or when a high-level wrapper explicitly owns the route |
| Test helpers | `TestConvex.layer(app)` discovers test helper entries from compiled component metadata where possible |
| IDs across the boundary | Treat component IDs as strings unless the wrapper can prove a safer branded mapping |
| Runtime methods | Promoted `.layer(options?)` values are Effect Layers with static install metadata attached; missing test or local implementations fail with `Convex.ComponentClientUnavailable`, not a thrown string |

## Caveats

- Promotion is a compatibility promise, not a claim that every upstream
  package has identical support depth.
- Prefer promoted `.layer(options?)` values for normal app code. The generic
  `defineComponentUse(...)` substrate is the escape hatch when a promoted
  wrapper lags a new upstream release.
- Runtime services should return schema-shaped component values and fail
  through Effect errors. If a method is intentionally not provided in a test
  layer, the default failure is `Convex.ComponentClientUnavailable`.
- If an integration depends on external webhooks or secrets, expect the docs
  to keep at least one explicit user-owned boundary instead of hiding
  everything behind a single magic resource.
