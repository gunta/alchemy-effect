This guide is for **Convex Plain**. Keep your existing
`convex/` directory, your existing Convex mental model, and your
existing `convex deploy` workflow. Alchemy manages the project,
deployment, environment variables, and surrounding infrastructure,
then bundles the app from the files you already own.

If you are starting a brand-new app, use
[Alchemy Convex Quickstart](/convex/guides/app-quickstart) instead.
That is the recommended **Alchemy Convex** golden path.
For a side-by-side of all four authoring modes, see
[Authoring Modes](/convex/concepts/authoring-modes). For the full
ownership model, start with [Convex Overview](/convex).

## What Convex Plain owns

With Convex Plain:

- You keep authoring `convex/*.ts` as you do today.
- Alchemy manages Convex project and deployment resources.
- Alchemy can manage Convex environment variables as resources.
- Alchemy can attach custom domains to the deployment when you want a
  stable production URL.
- Alchemy deploys your app by pointing `Convex.Bundle` at `./convex`;
  the bundle action hashes the source directory so file changes show
  up in the Alchemy plan.
- You can compose Convex with the rest of your stack in one
  `alchemy.run.ts`.

This is the right fit when you already have a Convex app in
production and want Alchemy to manage infrastructure around it
without forcing a DSL migration on day one.

## Prerequisites

- A working Convex app under `./convex`
- Bun installed
- An Alchemy stack entrypoint such as `alchemy.run.ts`
- Convex credentials that let Alchemy create or select a project and
  deployment

## Install the packages

```sh
bun add alchemy convex effect @alchemy/convex-plain
```

Convex Plain uses `@alchemy/convex-plain`, a small compatibility package
over the core `alchemy/Convex` provider resources. There is no DSL, no
generated file sink, and no runtime deploy protocol here.

## Start from your existing `convex/` app

Assume you already have something like this:

```txt
.
├── alchemy.run.ts
├── convex
│   ├── schema.ts
│   ├── notes.ts
│   └── http.ts
└── package.json
```

Alchemy treats `convex/` as **user-owned source** in Convex Plain. It
reads from that directory and deploys it, but it does not generate
over it.

## Create the Convex project and deployment

The core pattern is:

1. Create or look up a Convex project.
2. Create the target deployment for the current stage.
3. Add environment variables as resources.
4. Bundle the existing `convex/` directory into that deployment.

```ts
// alchemy.run.ts
import * as Alchemy from "alchemy";
import * as Convex from "@alchemy/convex-plain";
import * as Cloudflare from "alchemy/Cloudflare";
import * as Config from "effect/Config";
import * as Effect from "effect/Effect";
import * as Layer from "effect/Layer";

export default Alchemy.Stack(
  "NotesApp",
  {
    providers: Layer.mergeAll(
      Convex.providers(),
      Cloudflare.providers(),
    ),
    state: Alchemy.localState(),
  },
  Effect.gen(function* () {
    const project = yield* Convex.Project("Project", {
      slug: "notes-app",
    });

    const deployment = yield* Convex.Deployment("Dev", {
      project,
      type: "dev",
    });

    yield* Convex.EnvironmentVariable("SiteUrl", {
      deployment,
      name: "SITE_URL",
      value: "http://localhost:3000",
    });

    yield* Convex.EnvironmentVariable("DatabaseUrl", {
      deployment,
      name: "DATABASE_URL",
      value: Config.redacted("DATABASE_URL"),
    });

    yield* Convex.CustomDomain("ApiDomain", {
      deployment,
      domain: "api.example.com",
      requestDestination: "convexCloud",
    });

    yield* Convex.CanonicalUrl("CanonicalApiUrl", {
      deployment,
      requestDestination: "convexCloud",
      url: "https://api.example.com",
    });

    const code = yield* Convex.Bundle("Code", {
      deployment,
      source: "./convex",
    });

    const assets = yield* Cloudflare.R2Bucket("Assets", {});

    const worker = yield* Cloudflare.Worker("Web", {
      bindings: {
        CONVEX: deployment,
        ASSETS: assets,
      },
      env: {
        CONVEX_URL: deployment.deploymentUrl,
      },
    });

    return {
      deploymentUrl: deployment.deploymentUrl.as<string>(),
      dashboardUrl: project.projectUrl.as<string>(),
      bundleHash: code.bundleHash.as<string>(),
      workerUrl: worker.url.as<string>(),
    };
  }),
);
```

Stack outputs are `Output<T>` accessors — call `.as<T>()` to give the
return type a stable concrete shape that downstream tests and tooling
can rely on. The same pattern is used in the [AiGateway binding test](https://github.com/Distilled-Cloud/alchemy-effect/blob/main/packages/alchemy/test/Cloudflare/AiGateway/AiGateway.test.ts).

Two details matter here:

- `Convex.Bundle` is the deployment step for your existing files.
- `Convex.EnvironmentVariable` makes app config visible in plans,
  state, and reviews instead of hiding it in an out-of-band dashboard
  step.
- `Convex.CustomDomain` manages the deployment's custom domain
  attachment; DNS records still live with your DNS provider.
- `Convex.CanonicalUrl` makes that custom domain the effective
  `CONVEX_CLOUD_URL` or `CONVEX_SITE_URL`. Set `url: null` to return
  to Convex's default URL.

## Why this is useful even without the DSL

Convex Plain is deliberately boring. That is its strength.

- You can adopt Alchemy without rewriting handlers.
- You can deploy Convex together with Workers, buckets, queues, and
  secrets in one stack.
- You can standardize stage, plan, review, and destroy workflows
  across your infrastructure.
- You can migrate selectively later: keep some files Convex Plain and
  move new surfaces to the DSL when it is worth it.

The design spec explicitly allows this mixed posture. Convex Plain is the
lowest-risk adoption path.

## Deploy

Run the normal Alchemy deploy:

```sh
bun alchemy deploy
```

Expected shape of the first deploy:

- Alchemy creates or adopts the Convex project.
- Alchemy creates the target deployment.
- Alchemy applies any `Convex.EnvironmentVariable` resources.
- Alchemy attaches any `Convex.CustomDomain` resources.
- Alchemy syncs any `Convex.CanonicalUrl` overrides.
- `Convex.Bundle` hashes `./convex` and runs a normal Convex code
  deploy when the source hash changes.
- The rest of the stack deploys in dependency order.

On later deploys, only changed resources should update. If your
Convex code and bundle options are unchanged, `Convex.Bundle` should
no-op.

## Plan before deploy

For teams that want reviewable infrastructure changes, run a plan
first:

```sh
bun alchemy plan
```

The intended UX is that Convex changes appear next to the rest of the
stack instead of being hidden behind a separate CLI run. In practice,
that means you can review:

- new or changed environment variables
- custom domain attachments
- canonical URL overrides
- bundle updates
- attached cloud resources
- stage-specific differences

from one plan surface.

## Destroy

When you want to tear down the environment, use the normal Alchemy
destroy flow:

```sh
bun alchemy destroy
```

The intended lifecycle is still resource-oriented:

- delete dependent cloud resources first
- delete the Convex deployment resources they rely on
- remove only what belongs to this stack and stage

For production systems, use stage separation and review just as you
would for any other Alchemy stack.

## When to move to Alchemy Convex

Convex Plain is a great steady state if your team likes raw Convex files.
Move to Alchemy Convex when you want:

- Effect Schema as the source of truth for database and function I/O
- generated typed refs and typed services
- migrations modeled as part of the app contract
- promoted component wrappers such as Better Auth, R2, and
  RateLimiter
- a single app declaration that explains schema, groups, HTTP routes,
  components, and migrations together

That path starts at
[Alchemy Convex Quickstart](/convex/guides/app-quickstart).
